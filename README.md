# Windows-Livestream-App
COMP-4990 (University of Windsor) "Project Management: Techniques and Tools" Course Project

# Introduction
This project aimed to explore the designing and building of a client-server application capable of broadcasting a device’s screen to another in real-time. From the beginning, we committed to developing the entire system from scratch, relying solely on low-level programming languages to gain a deeper understanding of how such applications function at their core. This decision required careful planning and the selection of tools that balanced functionality with performance.
Our primary focus was on creating an application that not only met its functional goals but also operated reliably and efficiently. Achieving this involved tackling challenges in areas like network communication, graphical user interface design, and real-time data processing. By looking into these aspects, we not only met the technical requirements of the project but also expanded our understanding of the fundamental principles behind software development. This report outlines the journey, including the tools we chose, the features implemented, and the difficulties we overcame to create this application.

# Technical Requirements
To develop the project, we chose C++ as the primary programming language due to its versatility and its compatibility with the graphical user interface (GUI) library selected for the application. C++ offered great performance and low-level control necessary for a project involving real-time data transfer and screen rendering. For handling network communication between the client and server machines, we used the Windows networking library, Winsock2. This is a well-established library that streamlined the process of establishing and managing socket connections. Winsock2 proved to be an effective solution for transmitting screen capture data efficiently over a network. For the GUI, we opted for wxWidgets, a comprehensive library that provided the necessary tools and frameworks to design and implement a functional and visually appealing interface. This choice allowed us to focus on customizing the interface to meet the application's specific needs.


# Key Features
The application had several features with the most notable being, screen capturing and transmission, a graphical user interface, real-time streaming, and support for multiple simultaneous connections.  The gdiplus library allowed for the capturing of the users computer screen. This library allowed us to create custom functions to create an image of the screen and then encode the data into an image format. Once the screen is captured, it is then sent to the client. Winsock2 is used to create the network sockets and allows for the transmission of data between machines. A GUI is then used to display the live stream on the client side. The interface creates a user-friendly way for the user to view the stream. To achieve continuous screen sharing, a timer was implemented to capture and transmit the screen captures several times per second.  Using multithreading, the server can handle up to three client connections at a time. Multithreading was required to allow for this feature. This would give each client its own process to send the data and avoid any miscommunication between connections.

# Difficulties Encountered
This project, like most, came with its fair share of challenges that required thoughtful problem-solving and adaptability. Initially, the application was developed using C. However, as the project evolved, it became apparent that the limitations of C, specifically its lack of modern libraries and tools, posed a challenge for achieving our goals. After much discussion and research, the decision was made to rewrite the application in C++. While similar in syntax and structure to C, C++ offered a more diverse range of libraries that were better suited to the project’s requirements. Additionally, it provided improved compatibility with the GUI library we ultimately selected.
Choosing the right GUI library proved to be another significant obstacle. When the project was still in C, the options for modern, functional GUI libraries were extremely limited. This restriction hindered our ability to implement a user-friendly and robust interface. However, once the application transitioned to C++, we had access to a wider selection of libraries. After testing and evaluating several options, wxWidgets was the best fit for our needs. This library provided the necessary tools to build an intuitive and responsive graphical user interface. The process of researching and experimenting with different libraries was time-consuming but ultimately rewarding, as it ensured the final product met our expectations.

# Implementation
Our codebase is primarily split between the server and the client. For the server, we initialize and create the server socket before listening for incoming connections. Once we accept an incoming connection, we create a new thread that will handle the sending logic for that particular client. The main thread will then continue to listen and accept incoming connections up to a maximum of 3 connections/ clients. For the client thread which handles the generation and sending of frames to the specific client, it calls the captureScreenToStream function in screencapture.cpp to generate the image of the server’s screen. It does so by using the Gdiplus library to retrieve the device context of the screen and copys the screen to memory as a bitmap. The encoder for image/jpeg is then retrieved and the bitmap is encoded by the encoder as an IStream/ memory stream. This way, the image remains in memory and can be used for network transmission. The remaining logic of the thread handles the sending of the stream/ image by first sending the size of the image before sending the contents in 4 MB chunks. This is then looped indefinitely until the client decides to terminate the connection, the client socket is closed and the thread is rejoined. 
The client is built upon the back of the wxWidgets library, whereupon initialization of the application, a thread is created to handle the networking logic. This thread initializes and creates the client socket before connecting to the server’s IP address. Upon connecting and telling the server to start streaming, the thread will continuously receive the image size followed by the image data from the server and store the image in a shared image buffer. As we will see later, the client needs to both read (to display the image on the GUI) and write (to update the buffer with the most current image received from the server) from this buffer on separate threads. Thus, this buffer is a critical section and needs to be atomized to ensure thread safety. Every time the image buffer is either updated or read, synchronization is utilized through a mutex for both operations (Seen in the ImageBuffer class for both methods). 
While the network thread is continuously updating the image buffer transmitted by the server, the main thread will display the stream of images by initializing the GUI window and binds multiple event handlers whenever the corresponding event occurs (initialization is done in the constructor of the StreamFrame class). The most important event is the timer event which triggers every 33 milliseconds (for 30 fps, client-side) from the refresh timer we set, which triggers the OnRefresh method/ event handler. This method will retrieve the most recent image in the global image buffer and displays it by refreshing the panel. Note that the image is decoded when creating the wxImage object which reads the jpeg data from the image stream in memory, and decodes it before being converted into a bitmap which wxWidgets can display. Other events bound include the resize and close event. The OnResize event handler will resize the panel to the current client window size, while the OnClose event handler will close the window and set the isRunning global atomic to false (also a critical section). Once set to false, the loop for the image-receiving logic in the network thread is broken, and the thread will then close the client socket before rejoining, thus terminating the connection.

# Conclusion
In conclusion, this project provided valuable insight into the challenges and rewards of developing a client-server application from the ground up using low-level programming languages. By working with C++ and leveraging libraries like Winsock2 and wxWidgets, we were able to create a functional and reliable system that captures, transmits, and displays live screen data in real time. Throughout the development of the project, we encountered and overcame significant obstacles, including the transition from C to C++, and the careful selection of tools and libraries that best suited our needs.
The project not only tested our technical skills but also deepened our understanding of network programming, GUI development, and the difficulties of real-time data processing. The experience of tackling these challenges has been both rewarding and educational, allowing us to gain a stronger foundation in software development. While the application successfully met its objectives, there remains room for future enhancements, such as optimizing performance or user interaction during the live-stream. Overall, this project was a great learning experience for us and raised our collaboration and technical skills to the next level.
